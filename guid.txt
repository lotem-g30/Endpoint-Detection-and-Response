## 1. EDR Architecture

### 1.1 What You Are Building

An **Endpoint Detection and Response (EDR)** tool is software that runs on a machine, monitors process behavior in real time, and alerts when it sees something suspicious. Your project is a minimal but realistic EDR built from two cooperating components:

- **Hook DLL** (`argus_hook.dll`) — injected into a process you want to monitor. Once inside, it intercepts Win32 API calls that attackers rely on and forwards them as structured events to the agent.
- **ArgusAgent** (`argus_agent.exe`) — the supervisor process. It receives those events, decides whether they are suspicious enough to warrant a scan, and runs three detection engines (memory scan, YARA, PE-sieve) against the suspect process.

The two components can never share memory directly — they are in different processes with separate virtual address spaces. All communication goes through a **Windows named pipe**, which the kernel manages. The hook DLL is the client; ArgusAgent is the server.

### 1.4 Why Two Processes?

You might wonder: why not run detection inside the hook DLL itself, in the same process?

1. **Stability** — if the detection engine crashes, the monitored process continues running. The agent crashing does not crash what you are monitoring.
2. **Privilege separation** — the agent can run with higher privileges than the monitored process, allowing it to open process handles for scanning.
3. **Centralization** — one agent can receive events from many hook DLL instances (one per monitored process) simultaneously.

This is why every production EDR (CrowdStrike Falcon, SentinelOne, Microsoft Defender) uses a similar split: a kernel or userland sensor that intercepts behavior, and a separate service that analyses it.

Right now each component lives in its own folder with its own `.sln` file. This makes it impossible to share header files between the DLL and the agent without copying them. When you change a shared type (like `ScanFinding`) you would have to update it in multiple places.

A single CMake project with a clear folder structure solves this:
- Shared headers live in `include/argus/` and are visible to both targets.
- The build system knows which libraries to link to which target.
- `cmake --build build` produces everything in one step.

## 3. Adding More Hook Detections

### 3.1 How API Hooking Works

When your hook DLL is loaded, it **patches the target process's memory** so that calls to certain Win32 functions are redirected to your own code first.

Microsoft Detours does this using a **trampoline**:

```mermaid
sequenceDiagram
    participant App as Application Code
    participant Trampoline as Detours Trampoline
    participant Hook as Your Hook Function
    participant Real as Real VirtualAllocEx

    Note over App,Real: Before hooking (normal call)
    App->>Real: call VirtualAllocEx(...)
    Real-->>App: return result

    Note over App,Real: After hooking (Detours installed)
    App->>Hook: call VirtualAllocEx(...) [redirected by Detours]
    Hook->>Hook: build JSON event, call eq_push()
    Hook->>Trampoline: call Real_VirtualAllocEx(...)
    Trampoline->>Real: jump to original code (bytes 6+ of VirtualAllocEx)
    Real-->>Trampoline: return result
    Trampoline-->>Hook: return result
    Hook-->>App: return result (application never knows)
```

The application calls `VirtualAllocEx` as normal. Detours has overwritten the first few bytes of that function with a jump to your hook. Your hook runs, records the event, then calls the original through the trampoline (which contains the overwritten bytes followed by a jump back into the real function). The application receives the correct return value and never knows the interception happened.

### 3.2 Why MessageBoxA Is Not Enough

MessageBoxA is a UI function. Real malware almost never calls it during an injection. The APIs that matter are at the memory and thread level:

```mermaid
flowchart LR
    A["Attacker / Malware"] --> B["VirtualAllocEx\n(allocate memory in victim)"]
    B --> C["WriteProcessMemory\n(write payload into that memory)"]
    C --> D["CreateRemoteThread\n(execute payload in victim)"]
    D --> E["Target Process\nrunning attacker code"]

    style B fill:#ff9999
    style C fill:#ff9999
    style D fill:#ff9999
    style E fill:#cc0000,color:#fff
```

Each of these three functions is a discrete step in the classic DLL injection technique — exactly what your `injector.exe` performs. Hooking them lets ArgusAgent see the attack as it unfolds, step by step.

### 3.3 Target APIs and What They Reveal

| API | Step | What to capture |
|---|---|---|
| `VirtualAllocEx` | 1 — allocate remote memory | target PID, address, size, protection flags |
| `WriteProcessMemory` | 2 — write payload | target PID, base address, byte count |
| `CreateRemoteThread` | 3 — execute payload | target PID, thread start address |
| `LoadLibraryA/W` | DLL load | DLL path |
| `NtAllocateVirtualMemory` | 1 (NT-level) | same as VirtualAllocEx; bypasses some userland hooks |

### 3.4 Hook Function Structure

Every hook follows the same pattern. Here is a concrete example for `VirtualAllocEx`:

```c
// 1. Save a pointer to the real function before patching
static LPVOID (WINAPI *Real_VirtualAllocEx)(HANDLE, LPVOID, SIZE_T, DWORD, DWORD)
    = VirtualAllocEx;

// 2. Write the detour function with the identical signature
static LPVOID WINAPI Hook_VirtualAllocEx(
    HANDLE hProcess, LPVOID lpAddress,
    SIZE_T dwSize, DWORD flAllocationType, DWORD flProtect)
{
    // 3. Call the real function FIRST so we can capture the result
    LPVOID result = Real_VirtualAllocEx(
        hProcess, lpAddress, dwSize, flAllocationType, flProtect);

    // 4. Build the JSON event (stack-allocated, no malloc inside the hook)
    char event[512];
    DWORD target_pid = GetProcessId(hProcess);
    snprintf(event, sizeof(event),
        "{\"api\":\"VirtualAllocEx\",\"pid\":%lu,\"target_pid\":%lu,"
        "\"address\":\"%p\",\"size\":%zu,\"protect\":%lu}",
        GetCurrentProcessId(), target_pid, result, dwSize, flProtect);

    // 5. Push to queue (never blocks — hook returns immediately)
    eq_push(&g_queue, event);

    return result;
}
```

### 3.5 Registering Hooks with Detours

All hooks must be installed and uninstalled inside a **Detours transaction** — a batch operation that patches all functions atomically:

```c
void hooks_install(void) {
    DetourTransactionBegin();
    DetourUpdateThread(GetCurrentThread());
    DetourAttach(&(PVOID)Real_VirtualAllocEx,    Hook_VirtualAllocEx);
    DetourAttach(&(PVOID)Real_WriteProcessMemory, Hook_WriteProcessMemory);
    DetourAttach(&(PVOID)Real_CreateRemoteThread, Hook_CreateRemoteThread);
    DetourTransactionCommit();
}

void hooks_uninstall(void) {
    DetourTransactionBegin();
    DetourUpdateThread(GetCurrentThread());
    DetourDetach(&(PVOID)Real_VirtualAllocEx,    Hook_VirtualAllocEx);
    DetourDetach(&(PVOID)Real_WriteProcessMemory, Hook_WriteProcessMemory);
    DetourDetach(&(PVOID)Real_CreateRemoteThread, Hook_CreateRemoteThread);
    DetourTransactionCommit();
}
```

`DetourUpdateThread` ensures the currently running thread's instruction pointer is adjusted if it happens to be inside one of the functions being patched — without this call, patching a function that is currently executing can crash the process.

### 3.6 What Not to Do Inside a Hook

Hook functions run inside the hooked thread. Certain operations are dangerous:

| Dangerous | Why | Safe alternative |
|---|---|---|
| `malloc` / `HeapAlloc` | The heap allocator may itself be hooked — calling it causes infinite recursion | Use stack-allocated buffers (`char event[512]`) |
| `WriteFile` directly to the pipe | Blocks the hooked thread; can deadlock the application | Push to `EventQueue`; drain thread writes asynchronously |
| `printf` / `OutputDebugStringA` | Slow; calls other Win32 functions that may also be hooked | Same — push to queue |
| Acquiring a lock that another hook also acquires | Deadlock if two hooked calls interleave | Use one lock only for queue index updates |

## 4. Adding Communication to Hooks

### 4.1 The Problem: Two Separate Memory Spaces

The hook DLL and ArgusAgent live in completely separate processes. Variables, pointers, and function calls do not cross that boundary. The only way to share data is through a **kernel-managed channel** — in this project, a Windows named pipe.

Think of the named pipe like a file that both sides can open by name: the agent creates it as a server, the DLL connects to it as a client, and after that both sides call `ReadFile`/`WriteFile` just like they would on a regular file. The kernel handles the buffering and synchronization.

### 4.2 Why Not Write Directly from the Hook?

A hook function runs on the same thread as the application code it intercepted. If we called `WriteFile` to the pipe directly from the hook, we would **block that thread** until the write completes. Named pipe writes can stall if the agent's read buffer is full or if the agent is busy. Blocking inside a hook can:

- Freeze the application's UI
- Cause timeouts in the monitored code
- Deadlock the application if the blocked thread holds a lock something else needs

The solution is a **producer-consumer pattern**: the hook function pushes an event into a thread-safe queue and returns immediately, while a background **drain thread** reads from that queue and writes to the pipe at its own pace.

### 4.3 Message Flow: Hook DLL to ArgusAgent

The following diagram shows the full lifecycle of one event — from the moment a hook fires to the moment ArgusAgent receives and processes it:

```mermaid
sequenceDiagram
    participant App as Application Thread
    participant Hook as Hook Function
    participant EQ as EventQueue
    participant DT as Drain Thread
    participant Pipe as Named Pipe (kernel)
    participant Srv as IPC Server Thread
    participant Agent as ArgusAgent Logic

    App->>Hook: calls VirtualAllocEx(hProc, NULL, 4096, ...)
    activate Hook

    Hook->>Hook: snprintf JSON event into stack buffer
    Hook->>EQ: eq_push(event_json)

    Hook-->>App: returns result (unblocked)

    loop Drain thread loop (background)
        DT->>EQ: eq_pop(buf)
        note over EQ: acquires CRITICAL_SECTION<br/>reads slots[tail]<br/>advances tail<br/>releases lock
        EQ-->>DT: returns true, fills buf
        DT->>DT: check eq_dropped() for new drops
        DT->>Pipe: WriteFile(pipe, buf + "\n")
        Pipe-->>DT: write acknowledged

    Srv->>Agent: forward enriched JSON object

        Agent->>Agent: enqueue ScanTrigger { pid: target_pid }
    else not a trigger
        Agent->>Agent: log event only
    end
```

### 4.4 The EventQueue in Detail

The `EventQueue` is a **fixed-size circular buffer** — an array of string slots with two integer indices tracking where the next write (`head`) and read (`tail`) happen:

```
Slots:  [ "event_A" | "event_B" | "event_C" |  empty   |  empty  ]
Index:       0            1            2            3           4
                                       ↑                        ↑
                                      tail                    head
                           (next pop here)           (next push here)
```

When `head` would advance past `tail`, the queue is full. Rather than blocking, the queue **drops the oldest entry** (advances `tail`) to make room — the hook function must never stall.

Both the hook thread (push) and drain thread (pop) access the queue concurrently. A `CRITICAL_SECTION` lock protects the index updates so neither thread sees a half-updated state.

The `eq_dropped()` counter tells the drain thread how many events were lost. When it increases, the drain thread emits a `{"type":"drop_notice","count":N}` line to the agent before the next event, so the agent knows the stream has gaps.

### 4.5 The Named Pipe Protocol

Every message is **one JSON object followed by a newline** (`\n`). This format is called NDJSON (Newline-Delimited JSON). The newline is the message boundary.

```
Bytes on the wire:
{"api":"VirtualAllocEx","pid":1234,...}\n{"api":"WriteProcessMemory","pid":1234,...}\n
├──────────── message 1 ─────────────┤  ├──────────── message 2 ────────────────┤
```

The agent's reader thread cannot assume one `ReadFile` call equals one complete message — the kernel may split or batch data. It must accumulate bytes into a local buffer and scan for `\n` to find message boundaries. This is the partial-read accumulation pattern described in detail in [`student-guide-ipc.md`](student-guide-ipc.md) Milestone 3.

## 5. Adding Detection Logic

### 5.1 What the Agent Does With Events

Receiving an event is not the same as detecting an attack. The agent must decide: is this event suspicious enough to scan? The answer depends on which API was called.

```mermaid
flowchart TD
    A["IPC Server reader thread\nreceives JSON event"] --> B{"check 'api' field"}
    B -->|"VirtualAllocEx\nWriteProcessMemory\nCreateRemoteThread"| C["This is a trigger API"]
    B -->|"LoadLibraryA\nor other non-trigger"| D["Log only\n(no scan)"]

    C --> E["Extract 'target_pid'\nfrom event JSON"]
    E --> F["Enqueue ScanTrigger\n{ pid: target_pid }"]
    F --> G["Scanner thread dequeues trigger"]
    G --> H["scanner_run_pid(pid, opts)"]

    H --> I["OpenProcess\nPROCESS_VM_READ |\nPROCESS_QUERY_INFORMATION"]
    I --> J{"ScanOptions flags"}

    J -->|"detect_private_executable"| K["memscan_run(hProc, pid)\nfind executable private regions"]
    J -->|"yara_rules != NULL"| L["yara_scan_process(hProc, pid)\nread regions, scan with libyara"]
    J -->|"detect_pe_anomalies"| M["pesieve_scan(pid)\ncompare in-memory PE vs disk"]

    K & L & M --> N["Accumulate ScanFindings"]
    N --> O["CloseHandle(hProc)"]
    O --> P["Serialize each ScanFinding\nto NDJSON stdout line"]

    style C fill:#ffcc00
    style D fill:#cccccc
```

### 5.2 How the Scanner Orchestrator Works

`scanner_run_pid` is the single entry point for "scan this PID now." It opens the process handle once (expensive — requires kernel privilege check) and passes it to all three sub-scanners before closing it. This avoids opening and closing the handle three times.

```c
int scanner_run_pid(DWORD pid, const char *session_id, const char *scan_id,
                    const ScanOptions *opts,
                    ScanFinding *out_findings, size_t *out_count, size_t max)
{
    HANDLE hProc = OpenProcess(
        PROCESS_VM_READ | PROCESS_QUERY_INFORMATION, FALSE, pid);
    if (!hProc) return -1;

    if (opts->detect_private_executable)
        memscan_run(hProc, pid, session_id, scan_id,
                    out_findings, out_count, max);

    if (opts->yara_rules)
        yara_scan_process(hProc, pid, ..., opts->yara_rules,
                          out_findings, out_count, max);

    if (opts->detect_pe_anomalies)
        pesieve_scan(pid, ..., out_findings, out_count, max);
        // pe-sieve opens its own handle internally

    CloseHandle(hProc);
    return 0;
}
```

Each sub-scanner appends to the **same** `out_findings` array, starting at `out_findings[*out_count]` and updating `*out_count` as it adds entries. A sub-scanner returning `-1` is logged as a warning but does not abort the others — each scanner is independent.

### 5.3 Memory Scanner: Finding Suspicious Regions

The memory scanner looks for regions that are:
- **Committed** (`MEM_COMMIT`) — actually in use, not just reserved
- **Private** (`MEM_PRIVATE`) — not backed by a file on disk
- **Executable** — protection flags include `PAGE_EXECUTE`, `PAGE_EXECUTE_READ`, or `PAGE_EXECUTE_READWRITE`

Legitimate code is always loaded from a file (DLLs and EXEs are memory-mapped — `MEM_IMAGE`). Private executable memory that appears out of nowhere almost always means someone wrote shellcode or a reflectively-loaded PE into the process.

```mermaid
flowchart LR
    A["VirtualQueryEx\nquery region at address"] --> B{"MEM_COMMIT?"}
    B -->|no| F["address += RegionSize\nquery next region"]
    B -->|yes| C{"MEM_PRIVATE?"}
    C -->|no| F
    C -->|yes| D{"Executable protect flag?"}
    D -->|no| F
    D -->|yes| E["Record FINDING_PRIVATE_EXECUTABLE"]
    E --> F
    F --> A
```

### 5.4 YARA Scanner: Rule-Based Pattern Matching

YARA lets you describe what malicious content looks like as a rule. The scanner copies each memory region into the agent's address space (using `ReadProcessMemory`) and then runs the compiled rules against those bytes.

**How to load rules at startup:**

```c
YR_RULES *g_rules = NULL;
yara_load_rules("rules/", &g_rules);   // pass a directory → loads all .yar files
```

**Example rule to get you started** — place it in `rules/basic.yar`:

```yara
rule MZ_in_private_memory {
    meta:
        description = "PE header found in private (non-image) memory — possible reflective load"
    strings:
        $mz = { 4D 5A }   // MZ magic bytes
    condition:
        $mz at 0
}

rule suspicious_string {
    meta:
        description = "Known-bad test string in memory"
    strings:
        $s = "ARGUS_TEST_PAYLOAD" ascii
    condition:
        $s
}
```

A YARA match produces a `FINDING_YARA_MATCH` entry with the rule name in `detail.yara_rule`.

### 5.5 PE-Sieve Scanner: PE Anomaly Detection

PE-sieve compares the in-memory image of every loaded module against its on-disk copy. If the code bytes differ, something modified the module after it was loaded — a classic sign of hollowing or stomping.

PE-sieve is written in C++, which is why its wrapper must live in a `.cpp` file. The `extern "C"` declaration on `pesieve_scan` makes it callable from your C17 agent code without name-mangling issues.

```mermaid
flowchart TD
    A["pesieve_scan(pid)"] --> B["PESieve_scan_ex(params)"]
    B --> C{"For each loaded module"}
    C --> D["Compare in-memory bytes\nvs. on-disk file"]
    D --> E{"Anomaly?"}
    E -->|"code bytes differ"| F["FINDING_PE_HOLLOWING"]
    E -->|"PE in anonymous memory"| G["FINDING_PE_IMPLANT"]
    E -->|"reflective stub pattern"| H["FINDING_REFLECTIVE_LOAD"]
    E -->|"clean"| I["skip"]
    F & G & H --> J["append to out_findings"]
    I & J --> C
```

### 5.6 Reading Findings Output

Each `ScanFinding` becomes one NDJSON line on stdout:

```json
{"ts":"2026-04-18T12:00:01Z","session_id":"sess-001","scan_id":"a1b2-...","pid":5678,"process_name":"test_target.exe","finding_type":"FINDING_YARA_MATCH","severity":"HIGH","region":{"base_address":"0x1400a0000","size":4096,"protect":64,"type":131072,"state":4096},"detail":{"reason":"YARA rule matched","yara_rule":"MZ_in_private_memory"}}
```

## 6. Preparing a Simple Test Suite

### 6.1 Test Pyramid

Build your tests from the bottom up. Each level depends on the level below it working correctly. Do not attempt end-to-end tests until the unit tests pass — otherwise you will not be able to tell which layer broke.

```mermaid
flowchart TD
    E2E["End-to-End Tests\nInject DLL → trigger API → observe finding\nDepends on everything below"]
    INT["Integration Tests\nHook DLL ↔ ArgusAgent over pipe\nDepends on unit tests"]
    UNIT["Unit Tests\nEventQueue, named pipe basics, JSON parsing\nNo external dependencies"]

    UNIT --> INT --> E2E
```

### 6.2 What to Test at Each Level

| Level | Test | Scope | Pass Criterion |
|---|---|---|---|
| Unit | EventQueue push/pop/overflow | In-process, no pipe | All 5 pops in order; `eq_dropped()=1` after overflow |
| Unit | Named pipe round-trip | Two executables, no hook | Server receives `"hello\n"` from client |
| Unit | JSON over pipe | Same, with cJSON | Server parses `"api"` field correctly |
| Integration | Drain thread delivery | DLL EventQueue + pipe server | 10 events arrive in order |
| Integration | IPC client retry | Client starts 1 s after server | Client connects within retry window; 5 events delivered |
| E2E | Hook DLL → ArgusAgent event | inject + trigger | `{"api":"VirtualAllocEx"}` appears in agent log |
| E2E | YARA detection | inject + allocate + write string | `FINDING_YARA_MATCH` for `MZ_in_private_memory` |
| E2E | PE-sieve detection | inject a DLL | `FINDING_PE_IMPLANT` in agent log |

### 6.3 Test Target Harness (`test_target.exe`)

Write a minimal target process you control completely. This gives you reproducible, predictable events to trigger:

```c
#include <windows.h>
#include <stdio.h>

int main(void) {
    printf("[target] PID = %lu\n", GetCurrentProcessId());
    printf("[target] Press ENTER to inject, then press ENTER again to trigger\n");
    getchar();   // pause here — inject argus_hook.dll now

    printf("[target] Calling VirtualAllocEx (suspicious self-allocation)...\n");
    LPVOID mem = VirtualAllocEx(
        GetCurrentProcess(), NULL, 4096,
        MEM_COMMIT | MEM_RESERVE, PAGE_EXECUTE_READWRITE);
    printf("[target] Allocated at %p\n", mem);

    // Write a string YARA can detect
    const char *payload = "ARGUS_TEST_PAYLOAD";
    SIZE_T written;
    WriteProcessMemory(GetCurrentProcess(), mem,
                       payload, strlen(payload) + 1, &written);
    printf("[target] Written test payload to %p\n", mem);

    getchar();   // pause — inspect ArgusAgent output
    VirtualFree(mem, 0, MEM_RELEASE);
    return 0;
}
```

### 6.6 Verifying YARA Detection Step by Step

1. Place `rules/basic.yar` (with the `MZ_in_private_memory` and `suspicious_string` rules from Section 5.4) in your project root
2. Start `argus_agent.exe` — confirm it logs `"YARA rules loaded"` (or similar)
3. Start `test_target.exe`, note the PID
4. Run `injector.exe <PID> argus_hook.dll`
5. Press ENTER in `test_target.exe` — `VirtualAllocEx` + `WriteProcessMemory` run
6. In `argus_agent.exe` output, you should see:
   - One event log line: `{"api":"VirtualAllocEx",...}`
   - One finding line: `{"finding_type":"FINDING_YARA_MATCH","detail":{"yara_rule":"suspicious_string"},...}`

### 6.7 Verifying PE-Sieve Detection Step by Step

1. Use `injector.exe` to load any DLL (even `argus_hook.dll` itself) into `test_target.exe`
2. ArgusAgent's scan of the target process should detect the injected module as `FINDING_PE_IMPLANT`
3. The `detail.pe_anomaly` field will describe which module PE-sieve flagged and why
